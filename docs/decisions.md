# 设计决策

记录"为什么这么做"，以及从参考代码（`ref/`）里保留了什么、丢掉了什么。
新增决策时追加在末尾，不修改历史条目。

## D1 文档主键用 URL 哈希，不用文件名或行号

**参考代码的问题**：`ref/crawler.py` 把 HTML 存成 `html_doc1`、`html_doc2`……文件名即主键，
于是三处下游代码都靠在文件名里找 `'html_doc'` 来排序（`ref/index.py:28`、
`ref/weighted.py:93`、`ref/weighted_bm25_search.py:110`），BM25 那份又从 `docid` 反推出
`'html_doc' + str(docid + 1)` 去找 URL。而 `crawled_count` 是先自增后写文件的，写失败就会
出现编号空洞，让"文件名排序"和"编号反推"同时失效。

**决策**：`doc_id = sha1(normalized_url)[:16]`，写进 `manifest.jsonl`，下游只从清单读主键。

**理由**：

- 主键由内容（URL）决定，不由存储顺序决定，因此跨 run 稳定、天然去重；
- 64 bit 空间下 10 万篇文档的碰撞概率约 2.7e-10，可接受，真撞了写入时能查出；
- 同一个值同时用于 zip 成员名，因此可以不解压整包就定位单页。

**代价**：必须先归一化 URL 再哈希。`http://ai.ruc.edu.cn` 与 `http://ai.ruc.edu.cn/`
若不归一化成同一个值，就会变成两篇文档。用的是参考代码里已验证的 `url_normalize`。

## D2 抓取产物用 zip + JSONL 清单

**参考代码的问题**：`data/` 那样的目录里散着几万个裸 HTML 文件，没有结构化元数据，
只有一份 `url_mapping.json` 记录"文件名 → URL"。要重建索引就得重新爬，或者保证这个
目录永不移动。

**决策**：`pages.zip`（每页一个成员）+ `manifest.jsonl`（每行一条完整记录）。

**理由**：

- `zipfile` 是标准库，逐成员流式读取，不需要解压到临时目录；
- JSONL 可追加写、可只读首行排障、可 diff；
- 压缩后体积通常降到原始 HTML 的 1/5 左右，备份和迁移成本大幅下降。

**考虑过但未采用**：`tar.gz`（随机读取要顺序扫描，建索引会变慢）、`zstd` 分片（需额外依赖）。

## D3 检索模型先做 TF-IDF，不做 BM25

**决策**：只实现一套标准 TF-IDF 余弦相似度，公式见
[architecture.md §4](architecture.md#4-检索模型tf-idf当前唯一模型)。

**理由**：参考代码里有 TF-IDF 和 BM25 两份实现，各自复制了一套
`Posting`/`InvertedIndex`/`Query`，改一处要改两处。先把一份做干净、做对（有测试、
有评测脚本），另一份才有对比的意义。BM25 不是被否定，是被推迟。

## D4 为拿分而加的启发式一律不进入主线

**参考代码的问题**：`ref/weighted_bm25_search.py` 文件头自述的"优化"包括
`sub_weight`、`sub_coverage`、`expand_df_threshold`、`sub_df_threshold` 四个阈值，
以及 `alpha = 4 - 0.25 * (n - 2)` 的覆盖率惩罚曲线和按 token 字符串长度判断日期粒度的
`_date_weight`。这些数值是针对当年那份固定题集调出来的，换语料即失效。

**决策**：主线只保留标准公式；上述启发式全部推迟，将来若加入，必须是
"默认关闭 + 可配置 + 有对比数据"的独立改动。

**理由**：不可解释的魔数会把代码变成不可维护的历史包袱，也违背本项目"学习"的定位——
学习的价值在于理解标准方法的来龙去脉，而不是复现当年的调参结果。

## D5 集中配置 + 依赖注入

**参考代码的问题**：路径散落在多处且基准不一致——`ref/crawler.py:106` 的
`checkpoint.pkl` 相对当前工作目录，同文件 `:285` 的 `html_doc/` 却相对脚本目录，
`ref/weighted_bm25_search.py:76` 又裸开 `'url_mapping.json'`。同时
`ref/crawler.py:327` 用 `fixed_delay=0.01` 覆盖掉了构造函数默认值 5，等于关闭限速，
而这件事在代码里完全不可见。

**决策**：`config.toml` 是唯一配置源，只有 `config.py` 读它；模块通过函数参数接收
配置对象；`--print-config` 打印合并后的生效配置。

**理由**：所有路径和阈值集中在一处，配合 `--print-config`，"实际生效的值是多少"
永远可查。不引入环境变量替换、配置继承、`include` 嵌套——需要区分环境时多一份
配置文件加 `--config` 即可。

## D6 分词与停用词的处理

**参考代码的问题**：`ref/word_filter_list.txt`（2389 行）并非一份中文停用词表，而是
"中文虚词表 + 整张英文停用词长表 + 二字母国家/域名代码片段 + PDF 转换噪声"的拼接物——
实测其中纯拉丁条目 1350 条，含汉字条目仅 860 条，且英文部分夹带 OCR 型残词
（`herse”`、`itse”`、`fify`、`amoungst`）。同时它缺少"的、了、是、在"这类单字虚词，
参考代码靠 `str_check` 过滤数字与符号，单字虚词实际都进了索引。

**决策**：`tokenizer/stopwords_zh.txt` 只保留中文（860 条通用 + 116 条单字虚词 +
93 条通用网页模板噪声词 = 1069 条）；噪声规则另放 `tokenizer/noise.py`，
只保留"不含拉丁字母或汉字即丢弃"这一条。

**理由**：本项目语料是中文网页，英文停用词层无用且带错，删除既是瘦身也是去污。
判定规则改用"必须含词字符"而非参考代码的 `isalnum()`——后者会漏掉 `++`、`---`、
`&&`、`&#`、`._` 这类含 ASCII 字母的纯符号串。停用词表是数据、噪声规则是逻辑，
分开存放便于独立调整；更激进的规则（例如丢弃单个 ASCII 字母）等有评测数据后再加。

**落实方式**：整理后写了 `tests/test_stopwords.py` 固化不变量——通用节必须无纯拉丁条目、
三节之间不得重复、虚词与模板噪声词必须在表内。一次性核查脚本用完即删，不进版本库。

## D7 状态与产物分目录

**决策**：`data/crawl/` 放抓取产物，`data/index/` 放索引产物，`data/state/` 放断点状态。

**理由**：三者的生命周期不同——抓取产物长期保留且需可重放，索引产物随参数变化频繁重建，
断点状态随时可丢弃。混在一个目录里既难清理也难判断"哪个文件能删"。

## D8 编码必须自己判定，不用 response.text

**问题**：实测 `ai.ruc.edu.cn` 返回 `Content-Type: text/html`，**不带 charset**。
requests 此时按 HTTP 规范退回 ISO-8859-1，于是整页 UTF-8 被解成乱码
（`ä¸­å½äººæ°`），并且乱码会被原样写进归档——错误就此固化。

**决策**：`crawler/fetcher.py::detect_encoding` 按"HTTP 头 charset → 页面内
`<meta charset=...>` → utf-8"的顺序判定，用 `response.content` 自行解码，
不调用 `response.text`。编码名先用 `codecs.lookup` 校验，解码用
`errors="replace"` 兜底。

**理由**：编码是"存档正确性"的地基，一旦写错，下游索引与检索全都建立在乱码上；
而这件事的判断成本很低，不值得依赖任何自动猜测（`charset_normalizer` 的
`apparent_encoding` 对短页面会给出危险结果）。

## D9 robots.txt 的判定要分三态，不能只有"有/无"

**问题**：实现 robots.txt 支持时，最初只用 `parser is None` 表示"无规则"，结果
**404 被当成禁止抓取**——而 404 的含义恰恰相反（站点没有 robots.txt，等于没有限制）。
这个 bug 是测试抓出来的，不是真实抓取抓出来的。

**决策**：判定结果用 `verdict` 三态表示：

| verdict | 触发条件 | 行为 |
|---|---|---|
| `loaded` | 取得 robots.txt 并解析成功 | 按 Allow/Disallow 判定 |
| `missing` | 404 等 | 视为无限制，允许抓取 |
| `unavailable` | 401/403、网络异常、URL 无主机名 | 按不允许处理 |

**理由**："取不到"与"没有限制"是两回事，混为一谈会造成两个方向的错误：把 404 当禁止
会让你白白放弃可抓的站点，把 403 当允许则是失礼。三态化之后每个分支的意图都能被单独
测试。

## D10 抓取顺序按 host 分组，而非轮转

**决策**：`frontier` 按 host 分桶，把当前 host 的待抓页面做完再切换到下一个 host。

**理由**：对单个站方而言，请求集中在较短时间窗内更易被其日志与限速策略容纳，也避免
"同时慢速骚扰多个站点"。代价是慢站点会拖住后面的站点；若将来确实需要公平轮转，只需
改 `Frontier.next_url` 一处（测试里已把这个行为固定下来并注明原因）。

## D11 主键取重定向后的最终 URL

**问题**：最初 `FetchResult.url` 存的是**请求 URL**，重定向目标被丢弃。后果是
`http://ai.ruc.edu.cn/` 与 `https://ai.ruc.edu.cn/` 会成为两篇内容相同的文档——真实
抓取里两者都出现过。这不只是浪费空间：重复文档会让 TF-IDF 的 `N` 与 `df` 同时失真。

**决策**：`FetchResult` 增加 `final_url`（取 `response.url`，缺失时退回请求 URL），
`doc_id` 由 `final_url` 计算，`RunRecord` 同时保留 `url`（请求来源）与 `final_url`
（内容所在）。

**验证**：单站点实测中，`http://www.cast.org.cn/` → `https://www.cast.org.cn/`、
`http://www.cipg.org.cn/` → `http://www.cicg.org.cn/` 两条重定向被正确记录，
30 条记录对应 30 个唯一主键。`final_url` 作为后加字段对旧清单保持兼容（缺失时回退为
`url`）。

## D12 写入前按主键去重，而不是依赖 zip 行为

**问题**：`zipfile.writestr` 遇到同名成员**不覆盖**，而是追加第二个同名成员；实测
`read()` 仍能取到内容（取到其中一个版本），但另一个版本成为清单无法访问的滞留数据，
且过程中只有一条 `UserWarning`。一旦两个入口落到同一主键，归档就会静默出现这种冗余。

**决策**：`Crawler` 维护本次运行已写入的 `doc_id` 集合，写入前判重；重复时记一条
"重复页面，跳过"的说明并计数。

**理由**：不把正确性建立在标准库的未定义细节上。这条规则同时是 D11 的必要配套——
引入最终 URL 作为主键后，重复主键才真正可达。

## D13 排队水位与抓取预算是两个概念

**问题**：最初把 `max_pages_per_host` 直接当作单 host 待抓队列上限。实测：首页 20 条
链接、上限 5 时，**20 条全部被拒**，且没有任何日志或计数。以默认值 50 抓一个列表页
有 500 条链接的站点，450 条会**永久丢失**（既不在队列里也不在检查点里，续爬补不回来）。

**决策**：两者分开——`max_pages_per_host` 是抓取预算，队列水位取
`max_pages_per_host * 10` 与 1000 的较大值；`Frontier` 统计被拒数量
（`dropped_count`），运行结束时若不为零则明确提示。

**理由**：水位只影响检查点文件大小（每条待抓记录几十字节），而静默丢链接会让语料
不完整且无从察觉。宁可让检查点大一点，也不要让"少收了数据"这件事无声发生。

## D14 路径基准统一为配置文件所在目录

**问题**：`config.toml` 里的 `data_dir` 等相对路径此前按当前工作目录解析，检查点里存的
`run_dir` 因此是相对路径（实测 `data\crawl\20260101-000000`）。所有入口恰好都以项目根为
CWD 时才正常，换个目录执行 `--resume` 就找不到归档。

**决策**：加载配置时把所有路径解析为**绝对路径**，基准为**配置文件所在目录**；命令行
`--seeds` 的相对路径遵循同一规则（`config.resolve_path`）。`Paths` 附带
`crawl_dir` / `state_path` 两个派生属性，取代原先在 `crawler/__main__.py` 里重复拼接的
`Path(settings.paths.data_dir) / ...`。

**理由**：以配置文件为基准而不是 CWD，是"换目录执行同一份配置应指向同一份数据"的唯一
一致做法；把派生路径挂到 `Paths` 上，则消除了四处重复拼接。实测从上级目录执行
`--resume`，能够正确定位到项目内的归档并继续。

**代价**：放在子目录里的配置文件，其相对路径基准是该子目录而非项目根（例如
`scripts/x.toml` 里的 `"data"` 会指向 `scripts/data`）。这是配置相对路径的通行语义，
也意味着临时配置应放在它假定的基准处，或直接写绝对路径。

## D15 用 ruff 与 mypy 做静态检查

**决策**：引入 `ruff`（选择 F/E/W/I/UP/B/SIM/C4/RET 规则集）与 `mypy` 作为开发期工具，
生产代码保持零告警。测试里不启用魔数（PLR2004）与未用参数（ARG002）检查——它们是测试
替身的固有噪声。

**已修**：未使用的 `lru_cache`／`timezone` 导入、导入排序、`functools.cache` 取代
`lru_cache(maxsize=None)`、`datetime.UTC`。

**未修（有意保留）**：`mypy` 对 `link_extract.normalize_url` 的 `urlunsplit` 调用与
`robots._crawl_delay` 的 `crawl_delay()` 返回值类型有误报（标准库存根与实际返回不符），
两处运行时行为都有测试覆盖，因此不为类型存根扭曲写法。

## D16 索引器只认清单，不认 zip 成员

**决策**：`indexing/reader.py` 以 `manifest.jsonl` 为文档集合的权威来源，只读取清单里
记录过、且 zip 里确实存在的成员；两种不一致都按"跳过"处理：

| 情况 | 处理 | 理由 |
|---|---|---|
| zip 里有成员、清单里没有 | 不索引 | 多半是中断留下的残片，没有被承认的元数据 |
| 清单里有记录、zip 里没有成员 | 跳过 | 不让单条坏记录中断整轮索引 |

**理由**：把"哪些算文档"这件事收归一处。参考代码里文档集合是由目录里的文件决定的
（`os.listdir` + 文件名解析），因此任何多余或缺失的文件都会直接改变索引内容；改为以
清单为准之后，索引内容只由清单决定，与文件系统的偶然状态解耦。

## D17 空归档不是错误

**问题**：一次都没抓到页面时，`pages.zip` 根本不存在——zip 句柄是在写入第一页时才建立的。
`read_documents` 直接打开该文件会抛 `FileNotFoundError`，把"空语料"误报成故障。

**决策**：`reader` 在 zip 不存在时返回空序列；`builder` 对空语料返回 `document_count = 0`
的空统计；CLI 在文档数为 0 时以退出码 1 明确告知"归档里没有可索引的文档"。

**理由**：`Archive` 的惰性建包是合理设计（一次空运行不该留下空 zip），因此"文件不存在"
必须被解释为"没有页面"，而不是"环境坏了"。这个 bug 是测试写出来才暴露的。

## D18 查询侧权重与文档侧不必逐项对称

**决策**：文档侧的词权重用线性词频 `w_tf * idf`，**不做**对数平滑；查询侧对重复词做
对数抑制 `(1 + ln query_tf) * idf`。

**理由**：两侧的"词频"含义不同，因此不必强行用同一个函数：

- 文档侧的 `title_tf * title_weight + body_tf` 已经是人工加权的量，再套一层对数会把
  `title_weight` 的效果压扁——这一点在测试里很直观：`title_weight` 从 0 扫到 50，
  排序的临界点落在 0.2 与 0.3 之间（`test_title_weight_reverses_the_ranking`）；
- 查询侧重复输入同一个词只是强调，用对数抑制比线性放大更符合直觉——重复一次不等于
  分数翻倍（`test_repeated_query_term_is_dampened_not_linear`）。

**代价**：两侧公式不同，读代码时需要同时看 `indexing/builder.py` 的范数计算与
`search/query.py`。为此把两侧的公式都写进了架构文档 §4，并在测试里以手算值固定
（`test_query_weight_uses_log_smoothing`、`test_idf_matches_formula`）。

**考虑过的替代**：文档侧也加对数平滑（教科书常见写法）。放弃的原因是对数会把
`title_weight` 与 `body_tf` 的差异压缩到不易察觉，而"标题命中应当更重要"正是本项目
想保留的可调行为。

## D19 检索不重新计算 idf，只用索引里的值

**决策**：idf 由 `indexing/builder.py` 在构建时算好并写入 `stats.json`；检索时直接读取。
`IndexStats.idf` 只是把 `TermStats` 里的值取出来，不重算公式。

**理由**：idf 的定义必须只有一处。参考代码里 `_extract_date`、`str_check`、覆盖率的
日期权重都在索引与查询两侧各写了一遍，任何一处改动都会让两侧口径悄悄分叉——而
"索引里算的和查询时算的不一致"是检索系统里最难察觉的一类错误。

## D20 单站预算是上限不是配额：总预算必须与站点数匹配

**问题**：多站点试跑设 `max_pages = 1000`、`max_pages_per_host = 250`，六个种子站点，
实测分布是 250 + 250 + 250 + 172 + 69，而排在后面的数学、统计、化院**各只抓到首页一页**。

**原因**：单站预算是"上限"而不是"配额"。六站 × 250 = 1500 超过了总预算 1000，于是谁先
被处理谁就吃掉大头；`frontier` 按 host 分组顺序处理，排在后面的站点自然饿死。

**决策**：在 `config.multisite.toml` 里写明关系——**总预算应不小于站点数 × 单站预算**，
试跑配置改为 `max_pages = 1500`。只记录经验，不在代码里自动分配配额。

**理由**：自动按站点数均分听起来聪明，但会引入隐式行为（改种子数就改变每站上限），也无法
表达"某站更重要"的意图。现在两个上限都是显式的，使用者知道关系即可——把关系写清楚，比
替使用者做决定更符合"简单可扩展"。

**考虑过的替代**：`frontier` 改为跨 host 轮转。它能缓解饥饿，但不能保证覆盖——总预算小于
站点数时总有站点抓不到。真正的修复是让两个预算的关系成立。

## D21 试跑产物不进版本库，只留可复现的配置

**决策**：抓取与索引产物（`data/`，多站点试跑约 8 MB zip + 索引 JSONL）不提交；
提交的是种子文件 `resources/seeds.multisite.txt` 与配置 `config.multisite.toml`，并把
复现命令写进 README。为方便人工查看，抓取日志 `multisite-crawl.log` 单独提交。

**理由**：产物是可再生的派生数据，体积随语料线性增长；而"怎么产生它"才是需要版本化的
信息。日志体积小（约 300 KB）且记录了真实抓取过程（限速、跳过、失败原因），对复盘有价值。

## D22 抓取预算必须按主机名计数，而不是 scheme + host

**问题**：`allowed_hosts` 与单站预算原先都按 `url_host`（scheme + host:port）分桶，于是
同一站点的 http 与 https 被视为两个 host，各拿一份预算。实测 `ai.ruc.edu.cn` 在两份预算
下被抓了 1168(https) + 1008(http) 页——单站上限 5000 形同虚设。同一问题还让待抓队列把
同一站点拆成两个桶。

**决策**：新增 `canonical_host`（小写、去端口、去 `www.` 前缀）用于**预算计数与待抓分桶**；
`url_host` 保持原语义（含端口）用于**限速**——端口不同可能是不同服务，限速按 origin 更合适。
两个函数的用途写进各自的文档字符串，避免再次混用。

## D23 索引阶段按内容哈希去重

**问题**：部分站点在 http 与 https 上提供**相同页面且不做重定向**（`ai.ruc.edu.cn` 如此），
两个 URL 的归一化结果不同，因此得到不同主键、各存一份。实测 8711 条记录里 2352 条
（27%）属于这种成对重复。后果不只是浪费空间：`N` 与 `df` 同时虚高，同一结果在检索里
出现两次（实测「人工智能 大模型」前两条就是同一篇）。

**决策**：`build_index` 默认按正文的规范化哈希去重（可用 `dedupe_content=False` 关闭）。
规范化只做空白折叠，不做语义处理。文档从 8711 降到 7438。

**考虑过的替代**：在抓取阶段把已知站点的 URL 统一改写成 https。那需要按站点维护改写规则，
且改错会漏抓；而"同内容只索引一次"在索引阶段就足以解决检索质量问题。

## D24 倒排表按字节偏移定位，查询不再全表扫描

**问题**：查询时只能用 `stats.json` 里的 idf 判断词是否存在，要拿倒排表就得在
`terms.jsonl` 里逐行找。8711 篇文档时该文件 65 MB，实测每次查询 1.7 秒——网页层无法接受。

**决策**：写出 `terms.jsonl` 时同时记录每个词条的**字节偏移**（`term_offsets.json`），
查询按词 seek 到对应行。查询降到 2–10 ms。写入与读取都用二进制模式：Windows 上 text 模式
会把 `\n` 写成 `\r\n`，偏移会每行差一字节，seek 后读到半行 JSON（这个坑在实现时立刻踩到，
并留下了 `test_term_offsets_point_at_the_right_rows`）。

**理由**：这是"数据布局为查询服务"的最小改动——不动打分、不动索引内容，只补一张偏移表。
偏移表 1.8 MB，换来两个数量级的查询提速。

## D25 被强杀的抓取会留下不可读的归档

**问题**：zip 的中央目录在关闭时才落盘。运行被强杀（`job_kill`）后，`pages.zip` 存在但
整体不可读，`ZipFile` 抛 `BadZipFile`；原实现把它当索引器故障抛出，掩盖了真实原因。

**决策**：`reader` 把不可读的 zip 与"zip 不存在"一样处理——返回空序列；CLI 以"归档里没有
可索引的文档"退出。同时在 `config.colleges.toml` 注释里写明**抓取务必跑到正常结束**。

**理由**：把"这一轮归档坏了"与"索引器有 bug"区分开，前者是数据问题、后者是代码问题。
逐条抢救半截 zip 不现实（没有中央目录就没有成员索引），因此只能整轮丢弃——这也是为什么
大预算抓取要留足时间，必要时用 `--resume` 分批跑。

## D26 滚动式修复之后做一次合并：共享启动流程与目录约定

**背景**：P5 之后连续做了六轮修复（预算生效、主机名口径、内容去重、查询提速、zip 容错、
抓取范围），每一轮都是"就地加一点"。加完之后出现了典型的漂移：同样的启动流程抄了四遍，
同样的时间戳目录逻辑写了两遍。

**决策**：做一次合并，只合并"确实逐字重复"的部分：

| 抽出 | 原先的重复 | 说明 |
|---|---|---|
| `cli.py` | 四个 `__main__.py` 各有一份 `load_settings` + `--print-config` 处理 | 用异常（`CliError`）而不是"返回可能为空的配置"，调用方写起来更直白，也不必 `type: ignore` |
| `runtime.py` | `Archive.create` 与 `writer._create_dir` 各写一份时间戳+序号；`latest_run` 与 `latest_index` 各写一份"取最新子目录" | 两个函数，都有两处调用 |
| `indexing/__main__.py` | 不需要再自己实现 `load_settings` | 直接复用 `cli` |

**刻意没做的**：没有把四个入口合成一个"通用入口"。它们的参数与业务分支本就不同
（crawler 有 `run`/`fetch` 子命令与种子报告，web 要启动服务），强行合并会引入一层
需要传回调的间接。**共享启动流程，不共享命令结构。**

**判断标准**：一处逻辑要抽出来，得满足"逐字或近乎逐字重复"且"有两处以上调用"。
按这个标准复核后，本轮也**没有**为下列候选引入抽象：`_is_html`/`_is_retryable`
（各一处且语义独立）、`url_host`/`canonical_host`（口径不同，见 D22）、`Progress`
（承载真实状态：计数与起始时刻）。

## D27 分词器在加载/构建时预热

**问题**：jieba 的词典在首次调用时才构建，约 0.8 秒。实测索引加载 207 ms，但**第一次**
查询 819 ms、之后 6–10 ms——这 0.8 秒会落在用户的首屏上。

**决策**：`load_index` 与 `build_index` 都先调用 `jieba.initialize()`，把这次开销并进
启动/构建阶段（加载变成约 970 ms，之后的查询都在 6–23 ms）。

**理由**：一次性固定开销放到"有明确开始与结束的阶段"里，比放在"第一个用户请求"里更好
解释也好观测——启动日志显示"索引已加载"时，后面的请求就都是稳定的了。
