# 设计决策

记录"为什么这么做"，以及从参考代码（`ref/`）里保留了什么、丢掉了什么。
新增决策时追加在末尾，不修改历史条目。

## D1 文档主键用 URL 哈希，不用文件名或行号

**参考代码的问题**：`ref/crawler.py` 把 HTML 存成 `html_doc1`、`html_doc2`……文件名即主键，
于是三处下游代码都靠在文件名里找 `'html_doc'` 来排序（`ref/index.py:28`、
`ref/weighted.py:93`、`ref/weighted_bm25_search.py:110`），BM25 那份又从 `docid` 反推出
`'html_doc' + str(docid + 1)` 去找 URL。而 `crawled_count` 是先自增后写文件的，写失败就会
出现编号空洞，让"文件名排序"和"编号反推"同时失效。

**决策**：`doc_id = sha1(normalized_url)[:16]`，写进 `manifest.jsonl`，下游只从清单读主键。

**理由**：

- 主键由内容（URL）决定，不由存储顺序决定，因此跨 run 稳定、天然去重；
- 64 bit 空间下 10 万篇文档的碰撞概率约 2.7e-10，可接受，真撞了写入时能查出；
- 同一个值同时用于 zip 成员名，因此可以不解压整包就定位单页。

**代价**：必须先归一化 URL 再哈希。`http://ai.ruc.edu.cn` 与 `http://ai.ruc.edu.cn/`
若不归一化成同一个值，就会变成两篇文档。用的是参考代码里已验证的 `url_normalize`。

## D2 抓取产物用 zip + JSONL 清单

**参考代码的问题**：`data/` 那样的目录里散着几万个裸 HTML 文件，没有结构化元数据，
只有一份 `url_mapping.json` 记录"文件名 → URL"。要重建索引就得重新爬，或者保证这个
目录永不移动。

**决策**：`pages.zip`（每页一个成员）+ `manifest.jsonl`（每行一条完整记录）。

**理由**：

- `zipfile` 是标准库，逐成员流式读取，不需要解压到临时目录；
- JSONL 可追加写、可只读首行排障、可 diff；
- 压缩后体积通常降到原始 HTML 的 1/5 左右，备份和迁移成本大幅下降。

**考虑过但未采用**：`tar.gz`（随机读取要顺序扫描，建索引会变慢）、`zstd` 分片（需额外依赖）。

## D3 检索模型先做 TF-IDF，不做 BM25

**决策**：只实现一套标准 TF-IDF 余弦相似度，公式见
[architecture.md §4](architecture.md#4-检索模型tf-idf当前唯一模型)。

**理由**：参考代码里有 TF-IDF 和 BM25 两份实现，各自复制了一套
`Posting`/`InvertedIndex`/`Query`，改一处要改两处。先把一份做干净、做对（有测试、
有评测脚本），另一份才有对比的意义。BM25 不是被否定，是被推迟。

## D4 为拿分而加的启发式一律不进入主线

**参考代码的问题**：`ref/weighted_bm25_search.py` 文件头自述的"优化"包括
`sub_weight`、`sub_coverage`、`expand_df_threshold`、`sub_df_threshold` 四个阈值，
以及 `alpha = 4 - 0.25 * (n - 2)` 的覆盖率惩罚曲线和按 token 字符串长度判断日期粒度的
`_date_weight`。这些数值是针对当年那份固定题集调出来的，换语料即失效。

**决策**：主线只保留标准公式；上述启发式全部推迟，将来若加入，必须是
"默认关闭 + 可配置 + 有对比数据"的独立改动。

**理由**：不可解释的魔数会把代码变成不可维护的历史包袱，也违背本项目"学习"的定位——
学习的价值在于理解标准方法的来龙去脉，而不是复现当年的调参结果。

## D5 集中配置 + 依赖注入

**参考代码的问题**：路径散落在多处且基准不一致——`ref/crawler.py:106` 的
`checkpoint.pkl` 相对当前工作目录，同文件 `:285` 的 `html_doc/` 却相对脚本目录，
`ref/weighted_bm25_search.py:76` 又裸开 `'url_mapping.json'`。同时
`ref/crawler.py:327` 用 `fixed_delay=0.01` 覆盖掉了构造函数默认值 5，等于关闭限速，
而这件事在代码里完全不可见。

**决策**：`config.toml` 是唯一配置源，只有 `config.py` 读它；模块通过函数参数接收
配置对象；`--print-config` 打印合并后的生效配置。

**理由**：所有路径和阈值集中在一处，配合 `--print-config`，"实际生效的值是多少"
永远可查。不引入环境变量替换、配置继承、`include` 嵌套——需要区分环境时多一份
配置文件加 `--config` 即可。

## D6 分词与停用词的处理

**参考代码的问题**：`ref/word_filter_list.txt`（2389 行）并非一份中文停用词表，而是
"中文虚词表 + 整张英文停用词长表 + 二字母国家/域名代码片段 + PDF 转换噪声"的拼接物——
实测其中纯拉丁条目 1350 条，含汉字条目仅 860 条，且英文部分夹带 OCR 型残词
（`herse”`、`itse”`、`fify`、`amoungst`）。同时它缺少"的、了、是、在"这类单字虚词，
参考代码靠 `str_check` 过滤数字与符号，单字虚词实际都进了索引。

**决策**：`tokenizer/stopwords_zh.txt` 只保留中文（860 条通用 + 116 条单字虚词 +
93 条通用网页模板噪声词 = 1069 条）；噪声规则另放 `tokenizer/noise.py`，
只保留"不含拉丁字母或汉字即丢弃"这一条。

**理由**：本项目语料是中文网页，英文停用词层无用且带错，删除既是瘦身也是去污。
判定规则改用"必须含词字符"而非参考代码的 `isalnum()`——后者会漏掉 `++`、`---`、
`&&`、`&#`、`._` 这类含 ASCII 字母的纯符号串。停用词表是数据、噪声规则是逻辑，
分开存放便于独立调整；更激进的规则（例如丢弃单个 ASCII 字母）等有评测数据后再加。

**落实方式**：整理后写了 `tests/test_stopwords.py` 固化不变量——通用节必须无纯拉丁条目、
三节之间不得重复、虚词与模板噪声词必须在表内。一次性核查脚本用完即删，不进版本库。

## D7 状态与产物分目录

**决策**：`data/crawl/` 放抓取产物，`data/index/` 放索引产物，`data/state/` 放断点状态。

**理由**：三者的生命周期不同——抓取产物长期保留且需可重放，索引产物随参数变化频繁重建，
断点状态随时可丢弃。混在一个目录里既难清理也难判断"哪个文件能删"。

## D8 编码必须自己判定，不用 response.text

**问题**：实测 `ai.ruc.edu.cn` 返回 `Content-Type: text/html`，**不带 charset**。
requests 此时按 HTTP 规范退回 ISO-8859-1，于是整页 UTF-8 被解成乱码
（`ä¸­å½äººæ°`），并且乱码会被原样写进归档——错误就此固化。

**决策**：`crawler/fetcher.py::detect_encoding` 按"HTTP 头 charset → 页面内
`<meta charset=...>` → utf-8"的顺序判定，用 `response.content` 自行解码，
不调用 `response.text`。编码名先用 `codecs.lookup` 校验，解码用
`errors="replace"` 兜底。

**理由**：编码是"存档正确性"的地基，一旦写错，下游索引与检索全都建立在乱码上；
而这件事的判断成本很低，不值得依赖任何自动猜测（`charset_normalizer` 的
`apparent_encoding` 对短页面会给出危险结果）。

## D9 robots.txt 的判定要分三态，不能只有"有/无"

**问题**：实现 robots.txt 支持时，最初只用 `parser is None` 表示"无规则"，结果
**404 被当成禁止抓取**——而 404 的含义恰恰相反（站点没有 robots.txt，等于没有限制）。
这个 bug 是测试抓出来的，不是真实抓取抓出来的。

**决策**：判定结果用 `verdict` 三态表示：

| verdict | 触发条件 | 行为 |
|---|---|---|
| `loaded` | 取得 robots.txt 并解析成功 | 按 Allow/Disallow 判定 |
| `missing` | 404 等 | 视为无限制，允许抓取 |
| `unavailable` | 401/403、网络异常、URL 无主机名 | 按不允许处理 |

**理由**："取不到"与"没有限制"是两回事，混为一谈会造成两个方向的错误：把 404 当禁止
会让你白白放弃可抓的站点，把 403 当允许则是失礼。三态化之后每个分支的意图都能被单独
测试。

## D10 抓取顺序按 host 分组，而非轮转

**决策**：`frontier` 按 host 分桶，把当前 host 的待抓页面做完再切换到下一个 host。

**理由**：对单个站方而言，请求集中在较短时间窗内更易被其日志与限速策略容纳，也避免
"同时慢速骚扰多个站点"。代价是慢站点会拖住后面的站点；若将来确实需要公平轮转，只需
改 `Frontier.next_url` 一处（测试里已把这个行为固定下来并注明原因）。
